# EmberPDF 실제 대용량 PDF 검증 — 2026-10-04

Downloads의 실제 PDF를 이용한 이번 범위에서 문서 열기, 여러 워크스페이스 전환, 휴면 복귀와 세션 복원 검사가 통과했다. 제품 동작을 수정할 실패는 재현되지 않았다. 전체 파일·페이지·사용 시간을 포괄하는 안정성 보증이나 메모리 상한 측정은 아니다.

## 환경과 입력

- macOS 15.7.5 (24G624), Apple Silicon arm64.
- 화면 검사: EmberPDF 0.9.0 (20) Release 앱을 별도 QA 식별자로 복제·재서명했다. 사용자 앱의 기존 작업 공간과 설정을 분리했다.
- 자동 검사: 현재 작업 트리의 앱 모델과 PDFKit을 사용하는 Debug XCTest. 화면 앱과 측정 프로세스가 다르다.
- Downloads에서 발견한 PDF는 382개, 약 13.42 GiB. 그중 큰 파일 16개와 나머지 20 MiB 이상 파일 중 크기를 분산해 고른 24개를 검사했다.
- 자동 검사 입력: **40개, 5,654,605,688바이트(5.266 GiB), 총 13,677페이지**. 파일당 약 20.2–538.7 MiB, 101–869페이지.
- 화면 검사 입력: 위 목록 중 큰 파일 **12개, 약 3.15 GiB**. Downloads 원본과 같은 내용의 APFS 복사본을 사용했다. 자동 검사는 Downloads 원본 경로를 직접 읽었다.
- 개인 파일명·경로·문서 내용은 이 기록에 포함하지 않는다. 입력 매니페스트와 사본은 Git에서 제외되는 로컬 `work/ember-stress-20261004/`에 둔다.

## 40개 문서 자동 부하 검사

`RealPDFStressTests.testLargeLocalPDFsAcrossWorkspaces`가 **10.537초, 실패 0건**으로 통과했다.

1. 10개씩 4개 워크스페이스에 비동기로 열고, 각 공간에 2개씩 총 8개 탭 스택을 만들었다. 문서 순서와 소속을 확인했다.
2. 모든 문서의 처음·중간·끝 페이지를 160×220 크기 요청의 썸네일로 래스터화했다. 총 **120개 페이지**를 검사했다.
3. 모든 탭을 두 차례 다시 방문했다. **80회 재방문** 동안 페이지 수, 읽던 페이지, 선택 페이지, 확대율과 스크롤 상태를 확인했다.
4. 일반 상태에서 열린 PDFKit 문서 수가 전체 워크스페이스를 합해 **3개 이하**인지 확인했다. 관측된 휴면 복귀는 164회, 관리자 휴면 처리는 복원 모델까지 합해 188회였다.
5. 비교 중 문서 보호 정책을 직접 설정해 보호 탭 4개와 활성 탭 1개가 critical 메모리 압력 신호에도 남는지 확인했다. 보호 해제 후에는 활성 문서 **1개**만 남았다. 이는 정책 검사이며 실제 5개 비교 화면 검사나 OS 메모리 부족 재현은 아니다.
6. 세션을 메모리 저장소에 저장하고 모델을 닫은 뒤 새 모델로 복원했다. **40개 문서 모두** 다시 활성화해 공간·스택·페이지·선택·확대·스크롤 상태가 유지됨을 확인했다. 실제 앱 재실행과 보안 북마크 경로는 앞의 12개 GUI 검증과 별개다.
7. 대표 문서 4개에서 검색을 실행했다. 각각 170·468·258·146페이지를 0.028–2.365초 안에 모두 스캔했다. 검색어 `PDF`의 결과는 모두 0개였으므로 결과 정확성을 증명하는 검사는 아니다. 탭 전환에 의한 **예약된 검색 취소**도 확인했다.

| 자동 검사 측정 | 결과 |
| --- | ---: |
| 4개 배치 열기 합계 | 0.432초 |
| 공간·탭 활성화 168회 중앙값 / 95백분위 / 최대 | 5.27 / 15.73 / 32.80 ms |

배치 열기는 가벼운 문서 정보 검사와 지연 로딩을 포함한다. 5.266 GiB 전체를 메모리에 로드하거나 모든 페이지를 렌더링한 시간으로 해석하면 안 된다. 원본 해시 검사와 GUI 검사가 먼저 실행되어 파일 캐시가 데워졌을 수 있다. RSS는 작업 직후 표본이며 중간 순간 최고값은 포착하지 않는다. 작은 썸네일의 렌더 시간과 화면 전체 렌더 시간도 다르다.

CoreGraphics가 상세 없는 PDF 경고를 한 차례 기록했다. 이 실행에서 페이지 접근·썸네일 생성 실패, 앱에 표시되는 문서 오류, 충돌 또는 검사 실패로 이어지지는 않았다. 모든 페이지의 시각적 정확성을 확인한 것은 아니다.

## 재현과 남은 범위

`Tests/HwattakPDFTests/RealPDFStressTests.swift`를 테스트 배치 목록에 등록했다. 매니페스트 환경변수가 있을 때만 사용자 실문서를 읽으며 기본 테스트에서는 건너뛴다. 매니페스트는 정확히 40개의 서로 다른, 잠기지 않은 PDF에 대해 `path`와 `bytes`를 가진 JSON 배열이다. 결과 보고서는 파일명·경로 없이 순번과 수치만 기록한다.

프로젝트 루트에서 테스트를 빌드한 뒤 다음 환경변수와 필터로 실행한다. PDFKit의 동기 파싱·렌더링은 즉시 중단할 수 없으므로 이번 실행은 별도 실행기로 **600초 프로세스 제한**을 걸었다. 테스트 내부의 480초 제한과 검색의 3초 제한은 동기 호출 사이에서만 확인된다.

```sh
EMBER_STRESS_MANIFEST="$PWD/work/ember-stress-20261004/manifest.json" \
EMBER_STRESS_REPORT="$PWD/work/ember-stress-20261004/stress-report.json" \
swift test --skip-build --disable-sandbox --filter RealPDFStressTests
```

로컬 근거: `gui-report.json`, `stress-report.json`, `stress-summary.json`, `stress-run.log`, `regression.log`, `original-integrity.json`, `static-validation.log` (모두 `work/ember-stress-20261004/`). 원본 해시 비교는 테스트 외부 실행기가 수행했다.

미검증 범위는 382개 전체 동시 열기, 100개 이상 탭, 모든 페이지의 장시간 고배율 스크롤, 실제 OS 메모리 부족·열·GPU·프레임 지연, 대량 편집·저장·OCR와 손상·암호화 파일이다. 이번 결과만으로 해당 범위까지 검증 완료로 표시하지 않는다.

# 실문서 검사와 함께 보기 페이지 위치 보존 — 2026-10-10

대상: EmberPDF 0.9.0 (build 46), macOS arm64.

## 검사 범위

- 사용자가 `~/Documents/PDF 파일 테스트용`의 대용량 PDF를 시험에 사용하도록 허용했다. 폴더에는 PDF 382개, 합계 13.612 GiB가 있다. 이 수치는 파일 목록과 크기 조회 결과이며 전부 열어 검사한 결과가 아니다.
- 사용자가 이후 **큰 파일 위주 최대 30개**로 범위를 지정했다. 지정 이전에 시작한 40개 검사는 이미 완료되었다. 이후 추가 일괄 검사는 하지 않고, 그 표본에 포함된 가장 큰 3개만 함께 보기 재현에 사용했다.
- 향후 opt-in 실문서 검사는 4–30개 manifest만 허용한다. 10개 이하씩 워크스페이스로 나누고 5개 이하씩 그룹을 구성한다. 준비 스크립트도 큰 파일 최대 30개만 선택한다. 100개 탭 등의 별도 부하 검사는 합성 문서를 사용한다.
- 사용자 PDF는 읽기만 했으며 편집·저장·OCR·외부 전송을 하지 않았다. 실행 중인 사용자 앱과 실제 세션을 조작하지 않았다. 개인 파일명·경로·문서 내용·화면은 무시되는 `work/real-corpus-20261010/`에만 남긴다.

범위 지정 전 실행된 40개 표본: 합계 **5.300 GiB**, 문서 메타데이터상 **15,415페이지**. 모든 페이지를 렌더링한 것은 아니다.

- 워크스페이스 4개, 탭 40개 가져오기 및 그룹·순서·선택 상태 검사 통과.
- 각 문서의 첫·중간·마지막 페이지 썸네일 **120개** 생성 통과.
- 탭 재방문 **80회**, 세션 복원 후 문서 재개 **40개** 통과.
- 검색 4개, clean 탭 휴면·재개와 메모리 압력 시 비교 문서 보호 검사 통과.
- 테스트 작업 시간 **7.617초**, 외부 프로세스 시간 **9.505초**, 작업 후 표본 RSS 최댓값 **307.4 MiB**.
- 원본 40개의 SHA-256·크기·수정 시간이 검사 전과 동일함을 확인했다.

결과: `stress-report.json`, `stress-process.json`, `integrity-after-report.json`. 실제 화면 입력 지연이나 순간 최고 메모리 사용량을 측정한 결과는 아니다. Instruments 장시간 검사와 전체 앱의 버벅임 해소를 보장하지 않는다.

## 발견·수정한 함께 보기 문제

가장 큰 PDF 3개(538.7·514.4·277.2 MiB)를 실제 SwiftUI `PDFKitViewer` 세 개에 표시했다. 가로로 긴 페이지가 초기 520×720 영역에서 위에 붙으면서 화면 중앙이 다음 페이지를 가리켰다. 0부터 세는 85쪽이 86쪽으로 바뀌고, 다음 크기 조절에서는 다른 크기의 86쪽을 기준으로 맞추어 기존 페이지가 좌우로 잘렸다.

- 자동 맞춤 뒤 선택 페이지를 실제 clip 좌표로 중앙에 배치한다. crop 원점·회전·배율은 뷰 좌표 변환으로 처리한다.
- 상태에서 페이지를 지정하거나 함께 보기의 다음·이전 이동을 사용할 때도 같은 정렬을 적용한다.
- 첫·마지막의 짧은 페이지는 문서 경계 때문에 완전히 중앙에 놓을 수 없다. 명시적으로 선택한 페이지를 해당 clip·문서·bounds가 유지되는 동안만 기억하며, 실제 스크롤·크기 변경·문서 교체 시 해제한다. 약한 참조를 사용한다.
- 수동 확대의 위치 복원, 고정 패널 제외, 원래 탭의 페이지 묶음·일반 viewport를 유지한다.

# EmberPDF 성능 감사 — 2026-10-10

대상: 0.9.0 build 46의 대용량 사용 경로와 build 47의 유휴 저장 수정. 기능 검사 통과와 체감 성능을 구분한다. 공개 Release 배포 기록은 아니다.

## 확인한 문제와 수정

`MultiDocumentWorkspaceState.synchronizeActiveWorkspaceRecord()`가 값이 같아도 `workspaces`를 다시 게시했다. 세션 저장이 이 함수를 호출하고, 변경 관찰자가 다시 650ms 지연 저장을 예약해 유휴 상태에서도 저장이 계속됐다.

build 47은 탭 ID·모델 참조·순서, 활성 탭, 그룹이 실제로 달라질 때만 레코드를 한 번 갱신한다. 문서 본문 저장 경로는 바꾸지 않는다.

| 재현 검사 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 명시적 저장 후 2.2초 대기 | 기록 횟수 1 → 4 | 1 → 1 |
| 실제 이름 변경 후 대기 | 정상 기록 이후에도 계속 기록 | 변경 1회 기록 후 멈춤 |
| 다른 창을 포함한 세션 저장 | 두 창 모두 반복 기록 | 두 창 모두 추가 기록 없음 |

수정 전에는 신규 검사 3개에서 assertion 4개가 실패했고, 수정 후에는 모두 통과했다. 메모리 기반 저장소로 실제 debounce를 기다린 검사이며 사용자 설정을 덮어쓰지 않았다.

## 환경과 범위

- Mac15,13, 메모리 24GiB, 논리 CPU 8개, macOS 15.7.5 (24G624).
- 사용자가 지정한 폴더에서 **용량순 상위 30개만** 선택. 총 6,305,279,603 bytes(5.87GiB), 10,565페이지. 추가 PDF는 검사하지 않았다.
- 파일당 약 122–539MiB. GUI 경로는 이 30개 중 가장 큰 3개(합계 1.30GiB)를 사용했다.
- 기존 사용자 앱은 종료하지 않았다. 별도 시험 프로세스와 창, 메모리 기반 세션 저장소를 사용했다. 원본 편집·저장·OCR·외부 전송은 수행하지 않았다.
- 검사 전후 30개 전부의 SHA-256·크기·수정 시각이 동일했다.
- 시작 시 시스템의 여유 메모리는 약 41%였고 열·성능 경고는 기록되지 않았다. 기존 swap 사용량은 약 16.4GiB였지만 과거 누적 상태이므로 이번 앱이나 검사 탓으로 해석하지 않는다. 다른 실행 앱과 캐시 상태를 통제한 실험은 아니다.

## 대용량 30개 검사

`RealPDFStressTests` 1개 시나리오가 build 47 수정 코드의 Debug 빌드에서 통과했다. 시나리오 내부 시간 31.45초. 이 시간은 사용자의 입력부터 화면 표시까지 걸리는 시간이 아니다.

| 동작 | 결과 |
| --- | --- |
| 3개 워크스페이스에 10개씩 열기 | 문서 순서·소속·그룹 유지 |
| 각 PDF의 처음·중간·마지막 페이지 | 총 90개 페이지를 실제 비트맵으로 생성 |
| 전체 문서 두 차례 재방문 | 60회, 페이지·선택·확대·스크롤 상태 유지 |
| 세션 복원 후 다시 활성화 | 30개 모두 복원 |
| 문서 휴면·재활성화 | 휴면 141회, 재활성화 126회 관찰 |
| 메모리 압박 정책 호출 | 보호 문서 유지, 보호 해제 후 활성 문서만 유지 |
| 검색 | 2개 완료, 1개는 약 3초 제한 뒤 취소; 탭 이탈 후 늦은 결과 반영 없음 |

일반 경로의 문서 로딩 예산은 3개로 검사했다. 비교 보호 정책 시험에서만 보호 문서 4개와 활성 문서 1개, 총 5개를 의도적으로 유지한다. OS 전체를 메모리 부족 상태로 만든 시험은 아니다.

작업 사이에 측정한 RSS 최고값은 **232.2MiB**였다. 외부 연속 샘플 수집이 이 실행에는 성공하지 않아 순간 최고값이나 physical footprint로 표현하지 않는다. 10,565페이지를 모두 렌더링한 것도 아니다. 검색 결과가 0개인 문서도 있으므로 검색 정확도 전반을 입증하는 결과로 재사용하지 않는다.

## 실제 PDFKit 화면 경로

Release 최적화·테스트 접근 허용 빌드로 실제 `PDFKitViewer`와 `NSHostingView`를 생성했다. 기본 화면 12회 표시, PDF 3개 함께 보기 8회 진입·종료, 크기 조절 80회·이동 80회, 강제 비트맵 렌더링 52회를 수행했다. 유휴 저장 수정 전의 화면 경로를 측정한 결과이며, 두 번째 실행은 프로파일 진단용이다.

| 항목 | 첫 측정 | 진단 재실행 |
| --- | --- | --- |
| 시나리오 시간 | 102.34초 | 65.42초 |
| 250ms 간격 physical footprint 최고 관측값 | 1,065.2MiB | 743.8MiB |
| 문서를 닫은 후 10초 구간 footprint 중앙값 | 71.6MiB | 91.8MiB |
| 종료 후 살아 있는 PDFView/host·문서 모델·PDFDocument | 모두 0 | 모두 0 |
| 첫 기본 화면 생성·레이아웃 | 6,806ms | 279ms |
| 함께 보기 종료 레이아웃 중앙값 / 최대 | 15.5 / 854.6ms | 6.7 / 82.4ms |
| 크기 조절 레이아웃 중앙값 / 최대 | 34.7 / 890.6ms | 12.3 / 364.8ms |

반복할수록 메모리가 계속 증가하는 패턴이나 마지막까지 남는 문서·화면 객체는 이 범위에서 관찰하지 못했다. 캐시·프레임워크 메모리까지 0으로 돌아오는 것은 아니며, 모든 종류의 누수가 없다는 증명도 아니다.

첫 실행에서는 6초가 넘는 메인 큐 지연이 있었다. 재실행에서는 첫 화면 지연이 재현되지 않았다. 그 사이 화면 제품 코드를 바꾸지 않았으므로 이를 build 47의 개선 효과라고 주장하지 않는다. 첫 표시와 일부 리사이즈는 추가 최적화·현장 재현이 필요한 부분이다.

화면 검사는 숨겨진 시험 창을 강제로 비트맵화한다. Instruments의 메인 스레드 CPU 표본 중 76.3%가 이 강제 렌더링 경로였다. 프로파일 기록 시작은 시험 시작보다 24.3초 늦어 첫 지연 구간을 놓쳤다. 따라서 실제 트랙패드 입력 지연·프레임률·첫 지연의 원인을 확정하는 자료로 해석하지 않는다.

## CPU와 기존 앱 관찰

별도 PDFKit 시험 프로세스의 유휴 CPU는 첫 실행에서 약 0.8–1.0%(논리 코어 하나 기준)였다. 이는 세션 저장을 가진 전체 앱의 수치가 아니며 build 47 전체 앱의 개선율도 아니다.

실행 중이던 사용자 앱을 약 20.2초 관찰한 값은 CPU 평균 **18.3%**, physical footprint 약 **1.21GiB**, 디스크 기록량 증가 700KiB였다. 사용자 활동과 원래 실행된 코드 버전을 통제하지 않았으므로 유휴 저장 버그 하나의 기여율을 계산할 수 없다. 이 프로세스를 재시작하지 않았으므로 수정 후 실제 앱 CPU 감소량은 아직 측정하지 않았다.

외부 측정 도구의 초기 CPU 표시 0.44%에는 Mach tick 변환 누락이 있었다. 이 장비의 timebase 125/3을 적용해 18.3%로 정정했다. 별도 계산 시험에서 `getrusage`와 대조했고 도구도 수정했다. 위 PDFKit 검사 내부의 CPU는 처음부터 `getrusage`를 사용해 영향이 없다. 초기 원자료는 오류 표시와 함께 로컬 작업 폴더에 보존한다.

## 재현 자료

개인 파일명·경로를 포함하는 manifest, 해시, 프로파일 원자료는 Git에서 제외된 `work/performance-audit-20261010/`에만 있다. 익명 결과는 `stress-after-report.json`, `native-baseline-report.json`, `native-profile-report.json`, `regression-after.log`, `integrity-result.json`에 기록했다. 네이티브 실행에는 240초 외부 제한을 두었다. 일부 실행에서는 외부 프로세스 연결이 실패했으므로 자동 메모리 상한 중단이 모든 실행에 적용됐다고 주장하지 않는다.

신규 `RealPDFResponsivenessTests`는 `EMBER_PERF_MANIFEST`·`EMBER_PERF_REPORT`, 기존 `RealPDFStressTests`는 `EMBER_STRESS_MANIFEST`·`EMBER_STRESS_REPORT`로 명시적으로 실행한다. manifest에 없는 파일을 자동 탐색하지 않는다. 일반 회귀 실행에서는 실문서 검사를 건너뛴다.

앱 산출물·설치 검증은 `work/performance-fix-build47/`에 기록한다.

## build 48 앱 소개 반영

앱 정보의 ‘최근 확인한 내용’에는 PDF 30개의 문서 전환·복원과 함께 보기 종료 후 메모리 감소 관찰을 짧게 소개한다. ‘시험 조건과 남은 과제’를 펼치면 검사 날짜, 당시 build 46–47, 장비, 실제 확인 범위와 첫 표시·일부 리사이즈 지연을 확인할 수 있다. 결과를 현재 모든 버전·문서의 성능 보장으로 표현하지 않는다.

한국어를 포함한 지원 언어 10개에 반영했다. 기존 소개 화면·언어 검사 14개가 통과했고, 밝은/어두운 화면 20개를 렌더링했다. 한국어 어두운 화면과 아랍어 밝은 화면을 시각적으로 확인했다. 새 벤치마크 수치나 추가 회귀 검사 수를 만들어 소개하지 않았으며 위 성능 측정은 당시 기록으로 유지한다. build 48 확인 자료는 `work/about-validation-build48/`에 보존한다.

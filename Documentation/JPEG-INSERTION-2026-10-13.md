# JPEG 사진 삽입 용량 개선 — 2026-10-13

EmberPDF 0.9.0 build 62는 조건에 맞는 JPEG를 PDF에 삽입할 때 원본 압축 데이터를 재사용한다. 사진을 다시 JPEG로 압축하지 않으므로 추가적인 JPEG 화질 손실이 없으며, 기존에 비트맵으로 변환하면서 발생하던 최초 저장 용량 증가를 줄였다.

[이전 파일 크기 점검](FILE-SIZE-AUDIT-2026-10-13.md)과 같은 1024×768 테스트 사진으로 비교했다. **301,569바이트 JPEG를 삽입한 PDF가 2,181,282바이트에서 307,583바이트로 줄었다.** PDF 전체 크기는 개선 전보다 약 85.9% 작고, 원본 JPEG보다 약 2.0% 크다. 증가분에는 PDF 페이지·주석·색 공간 등의 구조가 포함된다.

## 측정 결과

크기는 모두 디스크에 저장된 파일의 바이트 수다.

| 작업 | 결과 | 확인 사항 |
| --- | ---: | --- |
| 원본 JPEG | 301,569 | 원본 테스트 사진 |
| 개선 전 최초 삽입 PDF | 2,181,282 | JPEG를 래스터로 변환한 기존 결과 |
| 개선 후 최초 삽입 PDF | 307,583 | 저장 PDF, 원본 JPEG 압축 데이터 재사용 |
| 같은 사진으로 10회 저장 | 매회 307,583 | 이미지 데이터 추가 누적 없음 |
| 재개방 후 크기 변경·저장 10회 | 최대 307,600 | 이미지 해상도·압축 데이터 유지, 주석 기하 정보만 변경 |
| 가로·세로를 각각 절반으로 자르기 | 532,862 | 512×384픽셀 자르기 결과, 숨긴 원본 픽셀 제외 |
| 사진 삭제 후 저장 | 2,362 | 삭제 결과, 이미지 리소스 제거 |

자른 사진은 보이는 픽셀만 담은 분리된 비트맵으로 저장하며 JPEG로 재압축하지 않는다. 따라서 이 사례에서는 **작게 자른 사진의 PDF가 원본 JPEG를 그대로 넣은 PDF보다 크다.** 이것은 반복 저장 누적이 아니라 저장 표현의 차이다. 자른 결과도 반복 저장 시 안정적으로 유지된다.

## 구현

[BoundedImageLoader](../Sources/HwattakPDF/Services/BoundedImageLoader.swift)의 삽입 전용 경로는 파일을 제한된 크기의 불변 데이터로 읽고, 미리보기와 압축 보존 후보를 같은 데이터에서 만든다. 이미지 종류·크기·방향을 확인하며 기존 파일 및 디코딩 예산을 우회하지 않는다. 메타데이터 제거 전후 색 공간을 `CFEqual`로 비교하여 색 해석이 달라지면 기존 래스터 경로를 사용한다. 일반 이미지 변환용 `load(at:)` 동작은 유지한다.

[PDFOriginalJPEG](../Sources/HwattakPDF/Services/PDFOriginalJPEG.swift)는 JPEG 압축 계수와 테이블을 보존한다. EXIF 방향 8가지는 PDF 그리기 행렬에 적용하므로 회전·반사된 사진도 픽셀을 재인코딩하지 않는다. 색 표현에 필요한 ICC, JFIF 기본 헤더, Adobe 정보는 보존하고, EXIF/GPS/XMP/IPTC·주석·내장 미리보기·파일 끝의 추가 데이터는 제거한다. Progressive JPEG의 여러 스캔과 스캔 사이 메타데이터도 처리하며, 잘못되었거나 지원하지 않는 구조는 압축 재사용을 포기한다.

[ImageStampAnnotation](../Sources/HwattakPDF/Services/ImageStampAnnotation.swift)은 자르기 영역이 정확히 전체 이미지일 때만 JPEG를 사용한다. 부분 자르기는 항상 보이는 픽셀만 가진 분리된 sRGB 비트맵으로 저장하여 숨긴 영역을 PDF에서 추출할 수 없게 한다. 문서·주석 사본은 불변 JPEG를 공유하되 자르기 상태와 래스터 캐시는 독립적으로 관리한다. 열려 있는 문서에서 자르기를 실행 취소하면 전체 이미지의 압축 데이터 재사용으로 돌아갈 수 있다.

[PDFWorkspaceState](../Sources/HwattakPDF/Models/PDFWorkspaceState.swift)의 사진 삽입에서 새 경로를 사용한다. 서명과 기존 이미지 초기화 경로는 압축 원본을 전달하지 않아 기존 동작을 유지한다.

## 적용 범위

- JPEG 원본 압축 재사용은 **8비트 RGB 또는 회색조**, 지원하는 방향·색 공간·JPEG 구조, 기존 픽셀 예산 안의 사진에 적용한다.
- 효율적 렌더링 설정에서는 최대 변 3,200픽셀·600만 픽셀, 일반 설정에서는 최대 변 4,096픽셀·1,200만 픽셀이라는 기존 디코딩 예산을 유지한다.
- CMYK, 다른 이미지 형식, 픽셀 예산을 초과하는 사진, 지원하지 않는 구조·색 해석, 부분 자르기는 기존 래스터 경로를 사용한다. PNG의 투명도를 버리거나 모든 사진을 JPEG로 재압축하는 변경은 없다.
- 매우 큰 원본 사진에 적용하던 기존 크기 제한은 그대로다. “추가 JPEG 화질 손실 없음”은 압축 데이터 재사용 경로의 성질이며 모든 크기의 원본을 항상 원본 해상도로 저장한다는 뜻은 아니다.
- 이미 이전 버전에서 PDF에 삽입되어 비트맵으로 저장된 사진은 자동으로 재최적화하지 않는다. 이번 개선은 새로 삽입하는 사진에 적용한다.

## 검증

최종 회귀 검사는 **중복 없이 81개 통과, 실패 0**이다. 서비스·모델 검사 57개와 실제 PDFView 상호작용 검사 24개를 별도 프로세스로 실행했다. 최초 확인용 실행의 테스트는 이 수에 중복 합산하지 않았다.

- [JPEGImagePreservationTests](../Tests/HwattakPDFTests/JPEGImagePreservationTests.swift): 저장된 JPEG 데이터 일치, 반복 저장·복사·크기 변경·자르기 실행 취소/다시 실행, EXIF 8방향, 회색조와 Display-P3, 투명 PNG, 픽셀 예산을 검사했다. 이미지 내용의 재압축 여부와 재개방한 PDF의 색·방향을 함께 확인했다.
- [PDFOriginalJPEGTests](../Tests/HwattakPDFTests/PDFOriginalJPEGTests.swift): progressive 스캔·압축 테이블 보존, 스캔 사이 메타데이터 제거, ICC 보존, JFIF 미리보기·MPF·파일 뒤 추가 이미지 제거, 잘못된 마커와 방향의 대체 경로를 검사했다.
- [PDFImageFileSizeTests](../Tests/HwattakPDFTests/PDFImageFileSizeTests.swift): 최초 삽입 용량, 반복 저장, 재개방 후 크기 변경, 자르기와 삭제를 실제 저장 파일로 측정했다.
- 기존 이미지 상호작용, 편집 기록, 복구 사본, 주석 개인정보, 이미지 변환, PDF 추가·추출, 본문 편집 용량 검사를 함께 실행했다.

실행 기록: 서비스·모델 57개, 이미지 상호작용 24개. 정적 검증도 통과했으며, 10개 언어의 지역화 키 일치와 버전 0.9.0 (62)를 확인했다.

실제로 저장된 개선 전후 PDF를 `PDFPage.draw`로 주석까지 포함해 2배 해상도(1224×1584)로 렌더링했다. 이 테스트 사진에서는 RGBA 픽셀 차이가 0이었고, 좌우 비교 이미지에서도 색·질감·배치가 같음을 확인했다.

검사는 합성 이미지·PDF로 실행했고 사용자의 원본 사진을 수정하지 않았다. 모든 외부 JPEG와 PDF 생성기 조합에 대한 보증은 아니며, 보존 조건에 맞지 않으면 기존 경로를 사용한다.

# PDF 구조 보존 확장 · build 78

2026-10-17. build 77에서 특수 구조 때문에 병합·추출을 안전하게 거절했던 실제 PDF 23개를 대상으로 보존 경로를 확장했다. 이 기록은 build 77의 [통합 검증](PDFCRAFT-INTEGRATION-2026-10-17.md)에 대한 후속 기록이다.

## 구현

페이지와 원본 CGPDF 문서의 출처를 분리해 기억하고, 저장 시 PDFKit이 만든 현재 페이지·주석·목차 구조에 원래 그림·글꼴과 문서 구조를 연결한다. 페이지 전체를 이미지로 변환하지 않는다. 앱 실행 시 외부 PDF 도구가 필요하지 않으며, qpdf·Poppler·pypdf는 검증에만 쓴다.

- 사용자 지정 페이지 번호는 선택·재배열·삽입 위치에 맞춰 계산한다. 이름 목적지와 첫 화면 이동은 포함된 페이지를 가리키도록 연결한다.
- 접근성 태그는 선택 페이지의 조상과 MCID 슬롯, 주석 OBJR, Form의 StructParents와 ParentTree를 함께 유지한다. 다른 문서의 역할·클래스·ID가 충돌하지 않도록 구분한다. 제외한 페이지로 연결된 항목은 제거한다.
- 원본 첨부의 실제 내용, AF와 파일 명세, 메타데이터, 출력 의도와 레이어의 기본 가시성·대체 설정을 보존한다. 소스별 레이어 설정은 다른 문서의 레이어를 바꾸지 않도록 범위를 제한한다.
- 전자서명은 원래 파일의 바이트 범위를 인증한다. 새 조립 문서는 서명되지 않았다고 표시하고, 서명된 입력 파일 전체를 바이트 그대로 첨부한다. 원래 서명을 새 파일에도 유효하다고 표시하지 않는다. 원본 서명의 암호학적 유효성을 검증하는 기능은 이번 변경에 포함하지 않는다.
- 본문 수정은 현재의 수정된 그림을 유지하면서 페이지 번호·첨부를 이어받는다. 수정한 페이지의 오래된 MCID 연결은 제거하고 수정하지 않은 페이지의 태그는 유지한다. 복구 사본과 재추출에서도 같은 원칙을 적용한다.

## 함께 수정한 문제

PDFKit은 저장하면서 0이 아닌 페이지 원점을 정규화하거나 인쇄 상자를 다시 계산할 수 있다. 주석이 없는 페이지는 현재의 5종 페이지 상자와 그림을 같은 원래 좌표계에 저장한다. 주석이 있는 페이지는 기존의 좌표 검증과 변환 경로를 유지한다. PDF 숫자를 고정 소수 자릿수로 반올림하면서 표본 렌더의 폭이 1픽셀 달라지는 문제도 수정했다.

전체 책의 이미지 이름표를 공유하는 문서는 선택한 3쪽만 추출해도 미사용 이미지까지 포함됐다. 단순 이미지 리소스임을 확인한 경우에만 최종 페이지들이 실제로 사용하는 Do 이름의 합집합을 남긴다. 복잡한 Form·패턴·Type3·마스크·주석 또는 알 수 없는 명령이 있으면 원래 리소스를 유지한다. 첫 대용량 표본의 3쪽 추출은 약 539MiB에서 13MiB로 줄었다.

원본부터 `/Dest [null ...]`인 목차 항목 5개 때문에 정상 목차까지 전부 거절되던 문제를 수정했다. 끊어진 항목만 제거하고 정상 목차를 유지한다. PDFKit의 위치·확대 API로 복사하면 `/Fit`이 `/XYZ`로 바뀌는 문제도 원래 보기 방식과 인수를 별도로 유지해 보완했다. 추출 시 의도적으로 제거한 링크는 재추출·병합 때 원본 캐시에서 되살리지 않는다.

한 원본의 첨부 이름 트리는 바이트 정렬이 올바르지만 혼합 인코딩 때문에 qpdf의 정규화된 이름 검사에서 경고가 났다. 이름이 유효하고 중복되지 않으며 바이트 이름 참조에 영향이 없음을 확인한 첨부 이름만 공통 UTF-16BE로 표현한다. 목적지의 원시 바이트 식별자는 그대로 유지한다. 이름 트리는 [ISO 32000-1 §7.9.6](https://developer.adobe.com/document-services/docs/assets/35e4369068f86065372c18787171a17e/PDF_ISO_32000-1.pdf)의 바이트 정렬·동등성 규칙을 계속 따른다.

카탈로그 복원 이후 독립 양식의 `/Rect`·`/Border` 등 같은 스칼라 배열이 별도 간접 객체로 저장돼 정식 양식 복원이 거절되던 회귀를 수정했다. 이 배열만 제한된 깊이·개수와 Reader 전체 비교 100,000회 상한에서 값으로 비교하며, 모양·글꼴·리소스 참조는 계속 같은 객체인지 검사한다. 서로 다른 사각형·테두리·모양 리소스가 합쳐지지 않는 역방향 시험도 추가했다.

90쪽 통합 표본에서는 한 입력의 전역 출력 프로파일이 다른 입력의 다섯 페이지에 작은 색 차이를 만들었다. 프로파일만 제거·재부착한 대조에서 원인과 재현을 확인했고, 원래 프로파일이 있던 아홉 표본 페이지도 함께 검사했다. 서로 다른 출력 조건을 섞을 때는 `EmberPDFSourceOutputIntents`에 전체 원본 프로파일 그래프와 해당 출력 페이지를 보관하고 전역 적용을 피한다. 단일 출처의 출력 조건은 유지하며, 보관된 조건은 재추출·재병합에서 페이지를 다시 연결하되 자동으로 활성화하지 않는다. [페이지별 OutputIntent는 PDF 2.0 기능](https://pdfa.org/how-to-get-started-with-pdf-2-0/)이므로 PDF 1.7에 이 키를 임의로 추가하거나 색을 추측해 변환하지 않는다. 혼합한 새 문서가 원본의 PDF/A·PDF/X 적합성을 유지한다고 인증하지 않는다. 이 표본에서의 픽셀 일치는 모든 인쇄 환경·프로파일의 보편적 동등성을 뜻하지 않는다.

## PDFKit 중단 조사

이전 중단과 독립 재현 모두 CoreFoundation의 `CFRelease(NULL)`에서 시작해 PDFKit의 `PDFTileSurface.releaseSurface` 등 상위 9개 이미지 UUID/offset이 일치했다. EmberPDF 문서 모델·변경점 서비스 없이 일반 PDFView만으로도 제한된 도구 실행 환경에서 재현됐다. 비트맵 캡처 없이 실제 페이지가 그려지는 경로에서도 발생했다.

동일한 컴파일된 시험 바이너리와 동일한 입력에서 제한 환경은 중단됐고 일반 macOS 호스트 실행은 통과했다. 제한 환경에서는 실제 64×64 IOSurface 생성이 실패했으며 정상 환경은 생성·잠금·해제가 성공했다. Metal 유무나 sysctl 경고만으로 원인을 판단하지 않았다.

제품은 프로세스당 한 번 실제 IOSurface 생성·잠금·해제를 검사한다. 실패하면 PDFView를 생성하기 전에 지역화된 안내를 보여 준다. 성공하면 기존 InteractivePDFView를 그대로 반환한다. 별도 감싸기 화면이나 지연 해제 경로를 추가하지 않는다.

별도 제어 시험에서 정상 환경 100회 표시·교체는 중단 없이 완료됐고 최종 PDFView 잔존은 0이었다. 제한 환경의 가드 적용 100회는 PDFView를 한 번도 만들지 않고 안내를 표시해 중단 없이 완료됐다. PDFKit 내부의 비공개 할당·해제 구현까지 관측한 것은 아니며, 작은 표면 검사의 성공이 향후 메모리 부족에 따른 모든 큰 타일 할당의 성공을 보장하지는 않는다.

앱과 동일한 네 가지 권한을 부여한 별도 QA 앱에서도 실제 App Sandbox 홈, IOSurface 생성·잠금·해제, PDFView 두 페이지 표시·검색·그리기를 확인했다. 정상 성능 시험에서는 3개 대용량 문서(합계 약 1.30GiB, 170·197·516쪽)로 PDFView 62개를 생성하고 네이티브 표시 52회를 수행했다. 종료 후 뷰·상태·문서 잔존은 모두 0, 최대 RSS는 약 303MiB였다. 이 시험은 네이티브 화면 준비와 전환 반응을 측정하며 전체 타일 렌더 완료나 프레임률을 측정하지 않는다.

## 검증

기존 시험 폴더의 382개·약 13.61GiB 가운데 이전과 같은 30문서(11,208쪽·5,375,774,121바이트)를 대상으로 검사했다. 각 문서의 첫·중간·마지막 페이지를 추출하고, 빈 첫 페이지가 있는 문서에 병합한 60개 출력과 선택한 90쪽을 한 문서로 합친 결과를 검증한다. 전체 11,208쪽을 모두 렌더링한 시험은 아니다. 원본은 읽기만 하고 출력은 별도 QA 디렉터리에 쓴다. 개인 경로와 PDF 본문은 배포 문서에 포함하지 않는다.

전체 회귀는 최종 소스와 같은 바이너리로 221개 클래스·93개 독립 프로세스를 실행해 **1,899개 통과·조건부 17개 건너뜀·실패 0개**였다. 실제 파일·네이티브 성능 등 별도 환경을 요구하는 시험은 위 명시적 QA 결과와 구분했다. 본문 편집·비교·양식·암호화 저장·주석·이력·복구·플러그인과 마우스·키보드 조작 검사를 포함한다.

패키지는 **0.9.0 (build 78), arm64, macOS 14.0 이상**으로 만들었다. 별도 출력 폴더의 앱과 ZIP은 ad-hoc 서명·권한 네 가지·10개 언어·ZIP 재추출 검증을 통과했다. ZIP은 21,413,811바이트이며 SHA-256은 `5a7e9c68f48595caec34ed7a99d7c96997c542bb45108733cf12c1f28e372a6f`이다.

Release 시험은 실제 패키지의 10개 `.lproj`를 복사·바이트 대조한 전용 XCTest 호스트에서 **259개 통과·조건부 2개 건너뜀**을 확인했다(261개 고유 사례, 재실행 중복 제외). 전체 본문·양식·카탈로그·복구 검사와 변경점 비교 15개·언어 전환 3개·네이티브 양식 입력 2개를 포함한다. 10개 언어의 300/340pt 패널을 그렸고 아랍어 RTL과 한국어 화면도 확인했다. 앱·시험 실행 파일과 486개 소스·시험·번역 파일의 동일성을 전후 검사했다.

시험 호스트의 절전 영향은 별도로 기록했다. 첫 한글 편집 사례의 1,009.847초는 실제 시스템 잠자기 1,012초와 겹쳤고, 같은 Release 바이너리의 독립 실행은 0.153초(프로세스 경과 0.23초·CPU 0.11초)에 완료됐다. 복구의 7초 QA 기한을 넘긴 초기 두 실행도 실패 로그를 보존했다. 마지막 복구 7개는 제품·시험 바이너리와 기한을 바꾸지 않고 모두 통과했다. QA 전용 활동을 시작·해제했지만 강제 Maintenance Sleep 7.037초가 여전히 관측돼 그 실행 전체 시간은 성능 표본에서 제외했다. 앱의 절전 정책을 바꾸지 않았다. [Apple의 활동 관리 API](https://developer.apple.com/documentation/foundation/processinfo/beginactivity(options:reason:))는 QA 호스트에만 적용했다.

Release 실행 기록은 `release-78-host-qa/`에, 패키지 식별자는 `release-package-identity.json`에 보관했다.

독립 검증 기록은 로컬 `work/pdfcraft-structure-expansion/`의 `catalog-structure-final.json`, `catalog-structure-combined.json`, `external-oracles-final/final-summary.json`, `external-oracles-final-combined-strict/report.json`, `external-oracles-final-profile-archive.json`, `final-source-identity.json`, `integrity-final.json`에 남겼다. 표본 이름·개인 경로·본문을 공개 문서에 옮기지 않았다. 초기 QA의 임시 디스크 부족과 수정 전 경고는 원래 실패 기록으로 남기고, 해당 출력은 최종 해시 기준으로 재검증했다.

## 지원 경계

XFA, 계산 순서, 복잡한 공유·계층 양식과 충돌하는 필드, 안전하게 합칠 수 없는 레이어 문맥, 손상되었거나 처리 상한을 넘는 그래프는 변경 전에 거절한다. 카탈로그 보존 writer에는 출력 1GiB·객체 250,000개 등 상한을 둔다. 문서의 암호화를 우회하거나 보존이 확인되지 않은 암호화·평탄화 저장 옵션과 조합하지 않는다.

실제 표본의 원본 오류도 구분한다. 한 문서는 원본부터 MCR이 실제 그림 리소스에 없는 별도 Form을 가리키고 같은 ParentTree 키를 공유한다. 해당 명시 참조와 스트림은 그대로 보존하고 실제 그림 Form의 키를 새 ParentTree에 연결한다. 원본에 없던 MCID 대응이나 접근성 정보를 추측해서 만들지 않는다. 독립 검증은 같은 페이지·MCID·스트림 SHA가 유지된 기존 문제만 별도 경고로 기록하며 새 손상은 실패로 처리한다.

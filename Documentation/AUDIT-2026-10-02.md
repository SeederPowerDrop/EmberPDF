# macOS·Apple Silicon·다중 대용량 PDF 검토

검토일: 2026-10-02. 대상: HwattakPDF 0.9.0 (build 20)의 현재 작업 트리.
기준 커밋은 `ffa69ed`이며, 이미 진행 중이던 검색·사이드바 변경도 포함해 검토했다.
제품 코드와 기존 사용자 변경은 수정하지 않았다.

**판정: Apple Silicon 네이티브 기반과 읽기 전용 다중 탭의 메모리 설계는 좋다.
그러나 여러 대용량 문서에 필기하며 공부하는 용도에서는 메모리 절약이 무력화되고,
자동 복구 저장·썸네일 생성 등에서 UI가 멈추는 경로가 있다.
최신 macOS 호환성과 장시간 자원 효율은 아직 검증 완료로 표시할 수 없다.**

## 호환성과 검증 범위

Apple의 [보안 업데이트 목록](https://support.apple.com/en-us/100100)은 검토 시점 최신 macOS를
**Golden Gate 27.0.1, 2026-09-28 배포**로 안내한다. 이 검토에 사용한 Mac은
**macOS 15.7.5 (24G624), arm64, Xcode 26.3, Swift 6.2.4, macOS SDK 26.2**다.

| 대상 | 확인한 내용 | 판정 |
| --- | --- | --- |
| Apple Silicon | 현재 소스 release 빌드 성공. `file`로 arm64 Mach-O 확인 | Rosetta 없이 네이티브 실행하는 구성 |
| macOS 14 | Package.swift와 Info.plist의 최소 버전 14.0 일치. Mach-O의 `minos`도 14.0 | 선언·빌드 확인, 이번 실기기 검사는 없음 |
| macOS 15.7.5 | 이번 자동 검사와 별도 재현에 사용 | 실제 검증 환경 |
| macOS 26 | SDK 26.2로 컴파일·링크 성공 | 해당 OS의 실행 검증과는 별개 |
| macOS 27.0.1 | Apple 최신 배포 버전 확인 | 실기기·VM 실행 및 SDK 27 빌드 미검증 |
| Intel Mac | 배포 스크립트가 arm64만 허용 | 현재 배포 대상 아님 |

Apple Translation은 14.4/15.0 availability 분기를 사용하며, 실제 바이너리에서도
Translation과 `_Translation_SwiftUI`가 weak linkage다. 검토한 경로에서 구형 macOS에
새 번역 API를 무조건 호출하는 문제는 발견하지 못했다.

AppKit·SwiftUI·PDFKit·Core Graphics·Vision 사용과 OCR의 utility 우선순위는
Apple Silicon에 적합한 출발점이다. 다만 Vision을 쓴다는 사실만으로 GPU/Neural Engine
사용률이나 전력 효율을 보장할 수 없다. Apple도
[실기기 Instruments 측정과 적절한 QoS 지정](https://developer.apple.com/documentation/apple-silicon/tuning-your-code-s-performance-for-apple-silicon)을 권고한다.
옵션인 Argos 번역 helper는 CPU 고정이며 GPU/ANE 가속 구현은 아니다.

## 우선 개선 사항

### 1. 높음 — 필기한 문서가 쌓이면 메모리 예산이 적용되지 않는다

`PDFWorkspaceState.canHibernate`는 수정된 문서를 제외하고,
`PDFTabMemoryPolicy`는 critical 메모리 압력에서도 이 제외를 유지한다.
수정 내용 보호 자체는 옳지만, 수정 문서를 디스크에 안전하게 보관한 뒤 휴면시키는
기능이 없으므로 목표 사용자의 일상적인 공부 흐름에서 기본 3개 예산이 효과를 잃는다.

이번에 빌드한 **실제 앱 클래스**에 작은 PDF 20개를 넣어 재현했다.

| 단계 | 메모리에 있는 문서 | 휴면 문서 | 정리 불가 문서 |
| --- | ---: | ---: | ---: |
| 20개 일괄 열기 | 1 | 19 | 0 |
| 20개 모두 한 번씩 읽기 | 3 | 17 | 0 |
| 각 문서에 형광펜 한 번씩 표시 | 20 | 0 | 20 |
| critical 메모리 압력 전달 | 20 | 0 | 20 |
| 테스트 문서 전체 저장 후 예산 적용 | 3 | 17 | 0 |

이는 문서 객체 수의 재현이다. 20개 실제 대용량 PDF의 RSS를 측정한 값은 아니다.
메모리 관리자는 창마다 생성되며 예산도 문서 개수 기준이다. 여러 창·네 문서 비교·
동시 OCR까지 합친 앱 전체 byte 예산은 없다.

개선: 원본을 임의로 저장하거나 dirty 보호를 제거하지 말고, 앱 전용의 검증된
스냅샷/편집 기록으로 미저장 상태와 실행 취소를 보존하는 휴면을 설계한다.
이어 창 전체를 합친 메모리 압력·작업 동시성 조정과 정리 불가 상태 표시를 추가한다.

근거: `PDFWorkspaceState.swift:381–394`, `PDFTabMemoryManager.swift:40–58,218–241`,
`TabbedWorkspaceView.swift:24,60–61`.
재현: `work/audit-2026-10-02/memory-probe/MemoryProbe.swift`, `result.log`.

### 2. 높음 — 자동 복구 저장이 공부 중 화면을 멈출 수 있다

자동 복구는 편집이 멈춘 뒤 5초, 500페이지 초과 문서는 60초 후에 실행된다.
하지만 실행 장소는 `@MainActor`이고, 전체 PDF 직렬화·검증·파일 쓰기가 동기적이다.
페이지 수가 적어도 이미지가 많은 200MB 문서는 5초 정책을 그대로 사용한다.

실제 `PDFRecoveryStore.save`와 `AtomicPDFWriter`를 호출하는 별도 재현에서,
**24페이지·75,537,704바이트(약 72MiB)의 합성 이미지 PDF 저장 한 번이
메인 actor를 2.19 / 2.43 / 2.23초 점유**했다. 입력 처리와 같은 실행 경로를
막는 연산임을 확인한 측정이며, GUI 전체 벤치마크나 일반 고객 문서의 평균은 아니다.
다른 검증 작업이 병행된 개발 환경에서 측정했다.

복구 파일의 한도는 개별 256MiB, 합계 1GiB이며, 직렬화한 뒤 검사한다.
따라서 한도를 초과해 거절될 문서도 전체 쓰기 비용을 먼저 낼 수 있고,
대용량 문서 여러 개의 미저장 내용을 전부 복구할 수 있는 저장소도 아니다.

개선: 원본/편집 데이터의 안전한 소유권을 유지하면서 복구용 불변 자료를 만들고
별도 worker에서 저장·검증한다. 변경분 기록과 byte 기반 지연 정책, 복구 한도 상태의
명확한 표시를 함께 검토한다. live PDFDocument를 무작정 detached task로 넘기면 안 된다.

근거: `PDFWorkspaceState.swift:215–236`, `PDFRecoveryStore.swift:72–100`.
재현: `work/audit-2026-10-02/memory-probe/RecoveryProbe.swift`, `recovery-result.log`.

### 3. 높음 — 썸네일 캐시가 비면 복잡한 PDF 렌더링이 입력을 막는다

썸네일 작업은 35ms 대기 뒤 메인 actor에서 `PDFPage.thumbnail`을 동기 호출한다.
대기는 아직 시작하지 않은 작업의 취소를 돕지만, 이미 시작한 렌더링 시간은 줄이지 않는다.

실제 `PDFThumbnailRenderingPolicy`와 PDFKit을 사용한 합성 벡터 PDF 재현:

| 한 페이지의 선분 수 | 요청 너비 160, 절약 모드 | 요청 너비 1200, 절약 모드 |
| --- | ---: | ---: |
| 10,000 | 약 7.6–7.9ms | 약 24.2–24.7ms |
| 100,000 | 약 82–85ms | 약 227ms |

10만 선분 페이지는 약 3MB다. 파일 용량만으로 렌더링 비용을 추정할 수 없음을 보여준다.
사이드바·개요에 여러 새 페이지가 나타나거나 편집으로 캐시 revision이 바뀌면
다른 문서의 입력까지 지연된다. 이 수치는 복잡한 합성 입력에 대한 개별 호출 시간이다.

개선: 별도 렌더링 문서/CGPDF 스냅샷을 사용하는 제한된 worker, 보이는 페이지 우선순위,
오래된 결과 폐기, 캐시 유지. 편집 중인 동일 PDFDocument를 여러 actor에서 공유하지 않는다.

근거: `PageThumbnailView.swift:13–14,62–65,140–148`.
재현 명령·결과: `work/audit-2026-10-02/render-probe/README.txt`, `results.txt`.

### 4. 중간 — OCR 준비·대량 PNG 출력·취소의 자원 관리가 고르지 않다

- PNG 출력은 선택한 모든 페이지의 렌더링·검증·쓰기 루프를 메인 actor에서 수행한다.
  많은 페이지를 출력하는 동안 다른 탭 조작과 취소가 처리되지 않는다.
- 한 페이지만 OCR해도 시작 전에 전체 PDF 스냅샷을 동기적으로 기록한다.
  OCR의 실행 상태/진행 표시를 설정하기 전이므로 준비 중 UI가 멈출 수 있다.
- 전체 OCR 취소는 Swift Task에 전달되지만 진행 중인 `VNImageRequestHandler.perform`의
  Vision request에는 전달되지 않는다. 현재 페이지 인식이 끝날 때까지 비용이 남는다.
  영역 OCR에는 이미 Vision request 취소 구현이 있으므로 공통화할 수 있다.
- 문서별 중복 실행 방지는 있지만 앱 전체 OCR 동시 작업 상한은 없다.

개선: 준비/출력도 진행·취소 가능한 파이프라인으로 만들고, 앱 전체 작업 예산과
Vision 요청 취소를 연결한다. 이 항목의 실제 대형 문서 지연·최대 RSS는 미계측이다.

근거: `PDFWorkspaceState.swift:1587,3538,3569–3575,3734`,
`SelectedPagePNGExporter.swift:116–139`, `PDFSecurity.swift:294–315`,
`VisionOCRService.swift:97,192–197,254–257`, `PDFRegionTextRecognizer.swift:199–225`.

### 5. 중간 — 관련 PDF 검색 캐시가 질의 사이에 버려진다

AI 보조의 관련 PDF 검색 handler가 호출마다 `LocalRelatedPDFSearchService()`를 만들고,
서비스 생성자는 새 `TransientPDFTextSampler` actor를 만든다. 따라서 32개 LRU 캐시는
다음 검색에서 재사용되지 않는다. 한 검색 안에서는 URL을 중복 제거하므로 캐시가
실제로 줄여 주는 작업도 제한적이다. 반복 질의 때 기본 최대 16개 문서 × 6페이지를
다시 읽을 수 있다. 새 actor가 여러 개 생기므로 모든 검색을 한 reader로 직렬화하는
효과도 없다.

개선: 서비스/샘플러를 workspace 또는 앱 수명으로 유지하고 기존 파일 서명 기반
무효화를 활용한다. 취소와 메모리 압력 시 캐시 정리도 같은 소유자에서 관리한다.

근거: `AIAssistantSessionModel.swift:336–341`, `LocalRelatedPDFSearchService.swift:24`,
`TransientPDFTextSampler.swift:44–73`, `PDFAIContextModels.swift:259–260`.

### 6. 높음 — 완료된 OCR 문서가 휴면하면 적용·내보내기가 막힌다

깨끗한 PDF에서 OCR을 마치면 checkpoint와 완료 상태만 저장하고 원본에는 아직 적용하지
않는다. OCR task가 종료되므로 이 문서는 휴면 대상이 될 수 있다. 이후 다른 탭을 열어
예산을 넘기거나 메모리 압력이 오면 문서 객체를 해제하고 revision을 변경한다.
다시 탭을 열 때 새 문서 객체와 revision이 생기지만 완료된 OCR의 식별 정보는 복구하지 않는다.

완료 결과 사용 조건은 예전 문서 객체·revision과의 일치를 요구한다. 따라서 탭에
완료 상태가 남아 있어도 적용/내보내기 버튼을 사용할 수 없다. 사용자가 OCR을 다시
실행하면 디스크 checkpoint를 재사용할 여지는 있으나 자동 복원 경로는 없다.
이는 코드 경로를 교차 확인한 기능 결함이며, 이번에 별도 GUI 재현은 하지 않았다.

개선: 사용 가능한 완료 결과를 가진 문서는 우선 휴면에서 보호하거나,
휴면 재개 시 원본 불변성을 확인한 뒤 checkpoint를 새 문서에 안전하게 연결한다.
단순히 revision 비교를 제거하면 다른 문서에 오래된 OCR을 적용할 수 있으므로 안 된다.

근거: `PDFWorkspaceState.swift:355–367,381–394,821–830,865–880,3598,3667–3674,3689,3772`,
`OCRSheet.swift:76–95`.

## 공부·비교 작업에 대한 평가

2–4개 비교 패널, 가로/세로 배치, 패널 크기·순서 조정과 스크롤 잠금은 용도에 맞는다.
다만 동기 스크롤은 **문서 전체의 같은 비율**을 맞춘다. 목차 길이·페이지 수가 다른
원문/번역문이나 다른 판본의 같은 내용을 자동으로 맞추지는 않는다.
페이지 오프셋 고정 또는 사용자가 지정한 대응 지점 연결을 추가하면 유용하다.
이는 현재 구현의 제품 범위이며 오동작으로 판정하지 않았다.
근거: `ComparisonModels.swift:61–63`, `PDFScrollSyncCoordinator.swift:184–201`.

문서 내 검색은 결과 상한, 페이지별 yield, 취소·세대 검증과 활성 PDFSelection 한 건 유지가
잘 구현되어 있다. 다만 `page.string` 추출은 메인 actor다. 과밀 합성 텍스트 페이지
12.6만 문자에서 37.8ms를 관찰했지만, 이를 일반 PDF 검색의 평균 지연으로 해석하지 않는다.

## 이미 잘 되어 있는 자원 관리

- 다중 열기는 경량 descriptor와 제한된 동시 검사로 시작하며 최종 활성 PDF만 로드한다.
- 읽기 전용 비활성 탭의 LRU 휴면, 메모리 warning/critical 대응이 실제 재현에서 작동했다.
- 편집 화면은 활성 탭 중심으로 생성하고 비교 화면은 선택된 최대 네 문서만 표시한다.
- 썸네일은 지연 생성, 전역 NSCache의 개수·비용 제한, 최대 치수·픽셀 수 제한이 있다.
  비용 한도는 OS 캐시와 뷰가 가진 이미지까지 합친 프로세스 RSS의 절대 상한은 아니다.
- OCR은 독립 스냅샷을 utility 작업에서 처리하고, 페이지별 autoreleasepool과 증분 checkpoint를 쓴다.
  절약 모드·저전력·심한 발열 시 12M pixels, 그 외 20M pixels로 래스터 비용을 제한한다.
- undo는 전체 문서 복제 대신 변경분 중심이며 문서별 22단계로 제한된다.
- Office 출력의 실제 UI 경로는 이미지 임시 파일과 비동기 ZIP 처리를 사용한다.
- 리소스 모니터는 표시 중에만 동작하며 타이머 tolerance로 불필요한 wakeup을 줄인다.

리소스 화면의 프로세스 CPU/RSS는 실제 카운터다. **탭별 메모리 수치는 파일 크기와
페이지 수로 계산한 추정치**이며, GPU·WindowServer·WebContent·압축 메모리 전체를
검증하는 도구는 아니다. 실제 검증에는 phys_footprint, peak RSS, 메모리 압력과
Instruments의 Allocations/Time Profiler/렌더링·에너지 지표를 함께 수집해야 한다.

## 데이터 보존과 배포 시의 한계

일반 저장은 임시 파일 검증·외부 수정 충돌 검사·원자적 교체를 우선한다.
단, 파일에만 권한이 있고 옆의 임시 파일을 만들 수 없는 경우에는 검증된 전체 Data를
원본에 직접 쓰는 fallback이 있다. 이 구간에서 강제 종료·전원 중단이 발생하면
원자적 교체와 같은 보호를 제공하지 못하며 전체 Data 보유 비용도 추가된다.
학습 필기가 중요하므로 앱 전용 복구본 또는 안전한 새 사본 저장 흐름을 우선 검토할
가치가 있다. 이번 검토에서 실제 데이터 손실을 발생시키거나 측정하지는 않았다.
근거: `AtomicPDFWriter.swift:100–131,179–201`.

배포 스크립트는 현재 `codesign --sign -`의 ad-hoc 서명을 사용한다.
Developer Preview라는 기존 안내와 일치하지만, 일반 사용자 배포의 첫 실행 경험은
Developer ID·Hardened Runtime·공증을 갖춘 패키지에서 별도 확인해야 한다.
이는 OS 실행 호환성 문제와 구분한다.
[Apple 배포·공증 안내](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

## 검증 기록

- 정적 프로젝트 검증 통과: 버전 0.9.0 (20), macOS 14.0+, 10개 언어 parity.
- 현재 작업 트리의 debug 테스트 빌드 및 release 빌드 성공.
- release 바이너리 확인: arm64, minimum macOS 14.0, SDK 26.2.
- 제품 코드 변경 없이 메모리 휴면·복구 저장·썸네일 재현을 수행했다.
- 자동 검사: **84개 클래스, 중복 제외 959개 테스트**. 재확인까지 합친 최종 결과는
  **957개 통과, 2개 조건부 제외**다. 한 번의 전체 실행이 무조건 통과한 것은 아니다.

첫 제한 환경 실행은 영역 선택 검사 중 HIServices XPC 연결 오류와 signal 5로
중단됐다. macOS UI 보조 서비스에 접근 가능한 호스트 환경에서 다시 실행했으며
해당 검사는 통과했다. 호스트의 document 배치에서는
`RecoverySchedulingTests.testRecoveryConfiguredAfterMarkingLoadedCopyStillCreatesSnapshot`
한 테스트의 두 assertion이 시간 초과로 실패했다. 로그에는 이 테스트 1,001초,
다른 저장 검사 1,037초 등의 비정상적인 경과 시간이 있다. 절전/호스트 스케줄링의
영향을 의심할 수 있으나 원인은 확정하지 않았다.

복구 클래스 7개 검사를 독립 재실행하니 57.6초에 모두 통과했다.
중단 뒤 미실행이던 workspace 130개, assistant 108개, plugin 73개도 각각 통과했다.
초기 실패는 삭제하거나 성공으로 덮어 기록하지 않았다. 간헐적인 복구 타이밍 실패의
원인 규명은 남아 있으며, 이번 결과를 완전한 안정성 보장으로 해석하면 안 된다.

두 조건부 제외는 기존 macOS 15 PDFKit offscreen tile teardown 문제 때문에 생략된
네이티브 두 페이지 표시와 포인터 중심 확대 검사다. 해당 GUI 동작을 검증한 것으로
집계하지 않았다.

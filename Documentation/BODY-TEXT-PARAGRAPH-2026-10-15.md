## 문단 편집 거절 원인과 구현 범위

기존 편집 경로는 선택 영역에 포함된 텍스트의 글꼴·크기·가로 배율이 모두 같고, 여러 줄의 시작점이 거의 같아야 문단으로 취급했다. 출판된 책의 일반적인 문단에도 한글과 숫자에 서로 다른 글꼴이 쓰이고, 숫자의 기준선이 약간 다르거나 첫 줄이 들여쓰기 되어 있어 이 조건을 벗어날 수 있다.

현재 구현은 하나의 제한된 문단으로 판단할 수 있는 텍스트를 원본 서식 구간(`InlineTextSourceRun`)으로 보관한다. 각 구간에는 글꼴, 크기, 가로 배율, 기준선 차이, 원본의 가로 진행 폭을 기록한다. 편집 미리보기와 저장할 PDF는 `PDFBodyTextAttributedLayout`을 함께 사용한다.

- 텍스트만 고칠 때 바뀌지 않은 앞·뒤 구간의 서식을 이어받고, 삽입된 부분은 변경 시작 지점의 구간 서식을 이어받는다. 여러 번의 변경으로 공통 앞·뒤 구간 사이가 넓어진 경우, 그 가운데 영역 전체를 하나의 변경 구간으로 취급한다.
- 첫 줄 들여쓰기와 일정한 줄 간격을 저장하고, 편집기와 PDF 출력에 같은 값으로 반영한다.
- 숫자 등 별도 글꼴 구간의 크기·가로 배율·기준선 차이를 유지한다. 로컬 대체 글꼴을 쓸 때에는 원본 구간의 가로 진행 폭을 기준으로 제한된 범위에서 폭을 보정한다. 더 긴 문구를 원래 단어 폭에 강제로 맞추는 방식은 사용하지 않는다.
- 사용자가 글꼴·크기·색상 등 서식을 명시적으로 변경하면 새 서식으로 초안 전체를 구성한다. 원본 구간별 서식 보존은 텍스트만 수정하는 경우에 적용한다.
- 일반 선택 경로와 태그가 있는 분절된 `BT`/`ET` 블록 경로에 같은 문단 기하 조건을 적용한다. 기존의 원본 변경 여부 검사와 안전한 콘텐츠 교체 경로를 유지한다.

이 변경은 임의의 복잡한 페이지를 문단 편집으로 허용하는 확장이 아니다. 현재 조건은 다음과 같다.

- 글꼴 이름은 달라도 허용하지만 크기와 가로 배율 비율은 각각 `0.8...1.25` 범위여야 하며, 정렬·글자색·배경색은 같아야 한다.
- 같은 줄의 기준선 차이는 1pt 이내, 줄 간격은 기준 글자 크기의 `0.8...2.5`배 이내이며 줄마다 거의 일정해야 한다.
- 이어지는 줄의 시작점은 1pt 이내로 일치해야 하고, 첫 줄과의 들여쓰기 차이는 `min(48pt, 글자 크기의 4배)` 이내여야 한다. 떨어진 두 단을 하나의 문단으로 합치지 않는다.
- 객체 순서·간격·의미 정보에 대한 기존 검사를 유지한다. 비공백 `ActualText`, 선택적 콘텐츠, 회전·기울임 등 기존에 거절하던 구조를 이 변경으로 허용하지 않는다.
- 해당 글꼴이 로컬에 없으면 대체 글꼴을 사용할 수 있으므로, 모든 원본 서체의 외형이 완전히 같아진다고 보장하지 않는다.

## 저장 후 재편집의 줄폭

저장한 PDF에서 다시 추출한 글자의 잉크 사각형은 마지막 글자의 실제 진행 폭보다 작을 수 있다. 이 사각형만 다음 편집의 줄폭으로 사용하면, 원문을 바꾸지 않은 줄도 마지막 한 글자가 다음 줄로 밀렸다. 편집기와 저장 경로는 원본 각 줄의 서식을 적용한 전체 진행 폭과 첫 줄 들여쓰기도 최소 줄폭에 반영한다. 측정할 때만 끝의 공백·탭을 제외하며 원문과 편집 데이터는 보존한다. CoreText가 줄바꿈을 포함한 PDF를 출력할 때 PDFium이 마지막 텍스트 객체에서 탭을 반환하는 경우도 별도 최소 예제로 확인했다.

PDFium이 숫자 객체의 추출 문자열 뒤에 덧붙인 공백은 실제로 다음 한글 객체 앞의 빈 공간을 나타낼 수 있다. 이를 숫자 글꼴의 공백으로 그리면 실제 사례에서 3.88pt가 2.575pt로 줄었다. 객체가 실제 소유한 문자와 추출 문자열의 공백 접미사를 구분하고, 그 접미사만 별도 서식 구간으로 분리해 원래 다음 객체까지의 간격을 유지한다. 숫자 자체의 글꼴·크기·가로 배율은 변경하지 않는다.

## 확대 흐림의 원인과 빌드 74 수정

읽기 테마의 `CIColorMatrix`를 PDFKit의 `NSClipView`에 적용한 기존 경로에서 확대 흐림을 재현했다. PDFKit은 확대 시 clip view 자체의 좌표계를 확대한다. 이 계층에 필터를 걸면 작아진 논리 좌표 크기로 합성한 결과를 다시 늘릴 수 있어, 원본이 벡터 텍스트여도 글자와 가는 선이 흐려진다.

빌드 74의 `PDFReadingDisplayFilterController`는 필터를 화면 크기를 유지하는 상위 `NSScrollView`에 적용한다. 이 스크롤 뷰는 확대되는 clip view를 담되 자체 bounds는 화면 크기로 유지한다. 문서 전체를 비트맵으로 바꾸거나 PDF 원본을 수정하지 않는다. 앱의 임시 선택·펜·텍스트 편집 오버레이는 필터 대상 바깥에 두며, PDFKit이 내부 clip view를 교체할 때 배경 보정과 복원을 별도로 처리한다.

`PDFReadingDisplayTests`에는 50%, 100%, 200%, 400%, 800% 확대에서 필터 대상이 화면 크기를 유지하는지, clip view에 필터가 들어가지 않는지, 선택·문서·배율이 보존되는지, 테마 전환과 내부 view 교체 시 필터·배경을 정리하는지 검사하는 항목이 있다. 이 기하·상태 검증과 실제 화면의 선명도 검증은 별개로 수행했다.

## 실제 172쪽의 CUA 화면 비교

별도 개발용 2열 비교 앱에서 동일한 PDF 페이지를 같은 크기와 배율로 나란히 표시했다. 읽기 필터를 100%에서 적용한 뒤 400%로 확대하여 동적 확대 경로도 확인했다. 원본 사용자 PDF는 수정하지 않았으며 비교 앱에는 동일 바이트의 임시 복사본을 사용했다.

| 비교 조건 | CUA 화면 확인 결과 |
| --- | --- |
| 빌드 72 방식의 clip view 필터 / 빌드 74 방식의 scroll view 필터 | 72 방식은 본문 글자가 명백히 흐렸고, 74 방식은 선명했다. |

이 결과는 실제 책 172쪽의 CUA 화면을 통한 시각 비교다. 화면 캡처의 수치 기반 픽셀 동일성이나 프레임 속도를 측정한 결과로 해석하지 않는다. 이번 비교에서는 빌드 74 경로의 추가 확대 흐림을 재현하지 못했으며, 추가적인 제품 렌더링 변경을 넣지 않았다.

검증용 소스는 `work/zoom75/LightZoomProbe.swift`에 있다. 초기 비교 앱의 화면 캡처 지연은 원본 Documents 경로를 여는 동안 메인 스레드가 파일 열기에서 대기하는 상태로 조사되었다. 별도 임시 복사본과 작은 2열 창으로 바꾼 뒤 CUA 캡처가 가능해졌으며, 해당 지연을 PDF 확대 성능 문제로 판단하지 않았다.

# 교재 PDF 드래그 화면 처리 개선 — 2026-10-14

EmberPDF 0.9.0 build 64는 종이색 보기에서 큰 교재의 글자를 계속 드래그할 때 발생할 수 있는 화면 처리 비용을 줄인다. 사용자에게 확인한 현상은 첫 클릭이나 마우스를 놓을 때만이 아니라 **드래그하는 동안 계속** 느껴지는 지연이었다.

## 조사와 변경

사용자가 지정한 Katz 교재는 163,282,501바이트·1,576페이지다. 실제 사용 설정은 종이색(`soft`)이었다. 읽기 전용으로 PDF의 본문(0부터 세는 페이지 966, 인쇄 페이지 938)과 목차를 사용한다.

기존 코드가 드래그할 때마다 PDF 전체를 복제하거나 OCR을 다시 실행하는 경로는 발견하지 못했다. 선택용 글자 위치와 보정 페이지는 최대 4페이지로 제한된다. 이번 프로파일에서도 드래그 중 물리 메모리가 계속 늘어나는 현상은 나타나지 않았다. 이것이 모든 페이지와 동시 작업 조건에서 메모리 압력이 없다는 뜻은 아니다.

- 종이색·세피아·야간 보기의 색상 필터를 PDFView 전체에서 **보이는 PDF 내용의 NSClipView**로 옮긴다. 글자 선택·펜·편집 도구는 필터 밖에서 그려져, 선택 표시가 바뀔 때 PDF 화면 전체를 함께 다시 보정하는 경로를 없앤다.
- 필터는 화면 크기로 제한되는 뷰에만 적용한다. 수천 페이지 길이의 PDFDocumentView에는 적용하지 않는다. PDFKit이 내부 뷰를 교체하면 필터 대상을 다시 연결한다.
- 여러 줄의 선택 사각형에는 공통 좌표 변환을 사용한다. 선택 범위가 바뀔 때마다 같은 선택 색상을 다시 계산하지 않는다. 글자 선택·단 구분·원문 보존 로직은 그대로 유지한다.
- PDF 내용, 이미지, 주석 및 저장 파일에 색상 보정을 기록하지 않는다. 현재 앱의 읽기 설정도 변경하지 않는다.

검증 과정에서 PDFView의 배경색 getter가 clip의 이미 보정된 색을 돌려주는 경우를 확인했다. 원래 canvas색을 controller에 별도로 저장하고, 이후 갱신·테마 변경·clip 교체에서도 같은 원색을 사용하도록 수정했다. 중간 측정은 `work/selection64/intermediate-canvas-fix/`에 분리했으며 최종 수치에 사용하지 않는다.

NSClipView가 처음 layer backing을 켤 때 0.15 화면 포인트의 픽셀 정렬이 관찰됐다. 필터가 없는 독립 probe에서도 같은 변화가 재현됐다. 회귀검사는 최초 한 backing pixel 이내 정렬을 허용하되 이후 30회 테마 변경에서는 위치가 누적 이동하지 않도록 검사한다. 독립 probe 100회 갱신에서도 위치는 고정됐다.

## 측정 방법

`PDFSelectionResponsivenessProfileTests`는 실제 SwiftUI 작업 화면과 PDFView에 120개의 서로 다른 드래그 끝점을 전달한다. 120Hz 이벤트 간격을 요청하며, 이벤트 처리·메인 큐·레이아웃·화면 갱신·Core Animation 제출 시간을 나누어 기록한다. 테스트 스케줄러가 실제로 처리한 이벤트 빈도는 화면의 FPS가 아니다.

이전 프로파일의 매 10번째 이벤트 강제 전체 화면 비트맵 생성은 제거했다. 선택 전후에만 이미지를 만들고, 강조 표시가 실제로 나타나는지와 옆 그림 설명이 선택되지 않는지를 검사한다. PDF 파일 버전·본문·주석·편집 상태가 유지되는지도 확인한다.

메모리 수치는 테스트 프로세스의 RSS와 물리 사용량이다. 창·PDFKit·썸네일·검증용 비트맵 비용을 함께 포함하며 설치 앱의 PDF 한 파일당 메모리로 해석하면 안 된다. macOS 화면 합성기의 GPU 처리 시간이나 물리적 입력부터 모니터 표시까지의 지연을 직접 측정한 결과도 아니다.

## 검증 결과

같은 Mac의 개발용 테스트 호스트에서 각 조건을 한 번씩 측정했다. 드래그마다 120개 이벤트 중 116번 실제 글자 범위가 바뀌었고, 드래그 중 작업 화면 알림은 0회·최종 선택 반영은 1회였다.

| 보기 | 이벤트 처리 p95, 변경 전 → 후 | 이벤트 시작부터 화면 제출까지 p95, 변경 전 → 후 |
| --- | --- | --- |
| 부드러운 종이 (`soft`) | 2.481 → **1.586ms** | 3.025 → **2.016ms** |
| 원본 색상 (`original`) | 1.371 → **1.437ms** | 2.452 → **2.290ms** |

종이색 보기의 이벤트 처리 p95는 이 실행에서 약 36.1% 줄었다. 같은 구간의 테스트 프로세스 CPU 시간(첫 클릭 포함)은 0.412초에서 0.362초로 줄었다. 원본 보기의 이벤트 처리 p95는 1.371ms에서 1.437ms로 소폭 증가했고 전체 제출 시간은 줄어, 이 실행만으로 원본 보기의 속도 개선을 단정하지 않는다. 측정 변동이 있으므로 모든 PDF의 동일한 개선율이나 PDF Expert 대비 우위로 해석하지 않는다. 요청한 120Hz에 대해 테스트 스케줄러의 실제 이벤트 처리 빈도는 전후 약 93–96회/초였으며 이는 FPS 측정이 아니다.

수정 후 종이색 보기의 물리 메모리는 드래그 직전 347.2MB에서 종료 직전 268.8MB로, 원본 보기에서는 342.1MB에서 267.9MB로 기록됐다. 전후 실행 모두 지속적인 메모리 누적은 관찰되지 않았다. 테스트 비트맵 및 시스템 캐시 회수가 영향을 주므로 메모리 감소량을 제품 최적화 성과로 주장하지 않는다.

선택 전후 이미지에서 본문 강조 표시를 확인했으며 옆 그림의 `Geographic / South Pole` 라벨은 변하지 않았다. AppKit의 비트맵 캡처는 `NSView.contentFilters`의 화면 합성 결과를 담지 않으므로, 종이색 필터의 GPU 출력 검증으로 사용하지 않는다. 필터 대상 분리·다시 연결·배경 복원은 뷰 구조 테스트로, 색상 수식은 Core Image 픽셀 테스트로 검증한다.

첫 클릭은 준비된 화면에서 종이색 보기 약 106ms·원본 보기 약 63ms, 마우스를 놓은 뒤 작업 화면 갱신은 각각 약 642ms·653ms로 남았다. 이번 변경은 사용자가 지정한 **드래그하는 동안의 반복 처리**에 집중하며, 클릭·놓기 지연까지 해결한 것으로 표현하지 않는다.

관련 원시 자료는 `work/selection64/before-soft.json`, `after-soft.json`, `before-original.json`, `after-original.json`과 각 `.before.png`·`.after.png`에 있다.

관련 XCTest **88개**가 통과했다. 중복 실행과 색상 모드별 프로파일 재실행은 개수에 더하지 않는다.

- 선택 모델·보정·미리보기 52개: 초기 실행의 실제 파일 선택 검사 2개는 명시적인 원본 경로를 전달해 후속 통과했다.
- 실제 PDFKit 상호작용 35개: 영역 선택 14, 기본 선택 알림 6, 실제 교재 2, 읽기 색상·뷰 교체·원본 보존 9, 선택 표시 좌표·색상 4.
- 실제 작업 화면 프로파일 1개: 종이색·원본 보기 각각 통과했다.
- 정적 검사: 버전·리소스·패키지 설정 및 10개 언어 문자열 일치 통과.

전체 저장소의 모든 테스트를 다시 실행한 결과는 아니다. 테스트별 최종 로그 경로는 `work/selection64/verification-summary.json`에 모았다.
